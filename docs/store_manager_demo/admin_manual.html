1
Fill the Create User form (left panel)
Enter Name, Email (unique), Phone, Employee Code, and a Temporary Password. Email cannot be changed after creation.
2
Assign one or more Roles
Click role chips to toggle them. Roles determine what screens and actions the user can access. A user can hold multiple roles — all permissions are merged.
3
Set Department scope (data isolation)
Select which departments this user can see. A Chef assigned only to "NORTH INDIAN" cannot view indents or stock from other departments. Leave unassigned for full visibility.
4
Activate / Deactivate accounts
Deactivated users cannot log in. Use this instead of deleting — it preserves all their history in audit logs and indents.
5
Reset Password on demand
Click "Reset Password" in the actions column. You'll be prompted to enter a temporary password. The user must change it on next login.
6
View Activity Log per user
Click "Activity Log" to open a modal showing every action that user has taken — indents submitted, stock received, approvals made — with timestamps.
Best practice: Always assign the minimum departments needed. Over-scoping gives users access to sensitive data from other outlets. The system admin (role key: admin) always bypasses all department restrictions.

1
Open the matrix from User Management
In the Create/Edit User form, click "View Permissions Matrix" (gold link, top-right of the Roles field). The full matrix modal opens over the page.
2
Read the grid: rows = permissions, columns = roles
Each row shows one permission (human label + machine key). Each column is a role. A checked checkbox means that role has that permission.
3
The Admin column is locked — never modify it
The admin role key bypasses all permission checks in code. Its checkboxes are greyed-out/disabled in the UI to prevent accidental restriction.
4
Toggle checkboxes to add/remove permissions
Click any non-admin checkbox to toggle it. Changes are local until you click "Save Permissions" — you can freely experiment before saving.
5
Save refreshes all active sessions instantly
After save, the backend invalidates permission caches. Logged-in users with that role get updated access on their next API call — no need to log them out.
Warning: Removing indent.approve from Store Manager means pending indents will not have any approver. Always ensure at least one non-admin role retains approval access, otherwise the workflow stalls.

1
Add a new department
Fill Department Name, a short Code (e.g. "RS" for Room Service), and optionally the Head Chef name. Click "Add Department". The new unit immediately appears in indent and issuance dropdowns.
2
Edit an existing department
Click "Edit" on any row — the form pre-fills. Update name, code, or chef assignment. Save with "Save Changes". Historical records using this department are unaffected (they store the name string).
3
The Code field drives indent grouping
Each indent request is tagged with the department name. The code is used in short references and reporting pivot tables. Keep codes uppercase and 2–5 characters.
4
Delete only unused departments
Delete is permanent and raises a confirmation dialog. If the department has linked indents, issuances, or user assignments, deletion will fail with a foreign-key error from the database.
Warning: Renaming a department code changes all future dropdowns but does NOT retroactively rename the string stored in past indent records. Rename codes with caution.

1
Add a supplier with full contact details
Fill Supplier Name (required), contact person, phone, email, GSTIN, and address. GSTIN is validated against the standard 15-character Indian format before saving.
2
Click a supplier row to expand the analytics dashboard
Clicking any row expands an inline analytics panel showing: Total Spend, PO count, Completed vs Pending orders, Fulfillment Rate (%), and Average Lead Time in days.
3
View Recent POs and click to open invoice detail
The left panel of the expanded view shows the last 10 Purchase Orders with status chips (Draft/Sent/Received). Click any PO row to open a full invoice modal with line items and totals.
4
Catalog: view all items & price history
The right panel lists every stock item this supplier has delivered, with last known price and trend arrow (↗ / ↘). Click an item row to expand its full price timeline with batch-by-batch cost changes.
5
Auto-Draft PO for all low-stock items
Click "⚡ Auto-Draft PO (Low Stock)" in the expanded header. The system scans all items linked to this supplier that are below their reorder threshold and creates a single draft PO automatically.
Best practice: Set a Preferred Supplier on each Reorder Point rule (Section 5). Then the Auto-Draft PO button knows which vendor to route the order to without manual selection.

1
Understand the three quantity fields
Min Qty — below this triggers the red alert banner. Reorder Qty — how much to order when restocking. Lead Time — supplier delivery days (for planning only, not auto-calculated yet).
2
Start typing an item name — it auto-fills the code
The Item Name field is connected to the live stock list via a datalist. Type a few letters and pick the matching item. The Item Code field fills automatically from stock records.
3
Set a Preferred Supplier for each rule
Select the vendor from the dropdown. This links the reorder rule to a supplier so that "Draft PO" and "Auto-Draft PO" know where to route orders without asking you every time.
4
Red alert banner shows real-time breaches
The amber/red banner at the top auto-loads on page open. It lists every item currently below its Min Qty threshold with current stock vs. minimum displayed as a chip.
5
Click "Draft PO" for a single-item order
"Draft PO" appears on rows that are breached AND have a preferred supplier. It creates a purchase order in Draft status for this item, pre-filled with the reorder quantity and last known price.
6
Enable / Disable rules without deleting
The "Disable" button sets is_active = false — the rule stays in the database but stops triggering alerts. Re-enable seasonally (e.g. mango season rules, Christmas extras).
Best practice: Review and update reorder quantities monthly. If your kitchen consumption pattern changes (e.g. new menu items), stale min_qty values will fire too many alerts or miss real shortfalls.

Choose a Lens (Tab) at the top of the dashboard
Procurement & Spend — supplier costs, PO volumes, price trends. Consumption Yield — how much each department consumed vs. what was issued. Variance & Anomalies — unexpected spikes, waste alerts, over-issue flags.

Use Global Slicers (left sidebar) to filter all charts at once

Export to PDF for management reports
The "Export to PDF" button (top-right) captures the current view including active filters and all visible charts. Use this for weekly management review packs.
Note: The BI Studio is read-only — no data is modified here. All charts pull from live production data, so reports reflect the exact current state of the database.

1
Five columns in every log row
Time — exact timestamp. Actor — the user who triggered the action (or "System" for automated processes). Action — machine key like indent.approve. Resource — table name + record ID. Department — if the action was scoped to a department.
2
Logs are immutable — nothing can be deleted
The audit_logs table has no delete or update API. Every write is append-only. This ensures accountability and tamper-proof history for compliance reviews.
3
Paginate 50 records at a time
Use the pagination buttons at the bottom to scroll back through history. Logs are sorted newest-first. 50 per page loads quickly even with thousands of entries.
4
Per-user Activity Log (from User Management)
For a filtered view of one person's actions, go to User Management → click "Activity Log" on that user. This shows only their actions — useful for investigating a specific incident without scrolling through system-wide logs.
Monthly practice: Review audit logs at least once a month. Look for unexpected roles.update or user.create entries — these indicate admin-level changes. Any change you didn't personally make should be investigated immediately.

Security Rules & Best Practices
How the permission system works and what admins must never do
Role Hierarchy & Access Model
Access Tier Overview

UNRESTRICTED
🏢
Manager / Store Manager
Cross-department access · Approve indents · Issue goods · Manage POs
ELEVATED
👨‍🍳
Chef
Own department only · Create indents · Log production · View own data

🚫 Never Do
✕Share the admin account across multiple people
✕Grant admin role to operational staff (chefs, store clerks)
✕Delete users who have placed indents or received stock
✕Leave "ChangeMe123!" as a permanent password
✕Modify the admin role key in the database
1
The admin role bypasses ALL checks in code
The backend's hasPermission() and frontend's hasPermission() both return true for any permission if the user has a role with key === "admin". This is hard-coded — no permissions matrix setting can restrict it.
2
Department scoping is enforced server-side
Even if a user somehow bypasses the UI, the backend's assertDepartmentAccess() function checks every indent/issuance API call. Chef assigned to TIFFINS cannot query RESTAURANT data via any path.
3
Never delete a user — deactivate instead
Deleted users break foreign keys on historical indents. Always use Deactivate. The deactivated user cannot log in, their token refresh will fail, and they will see "Account inactive" on next attempt.
4
Protect the last admin account
The backend runs ensureNotLastAdmin() before any user role removal or deactivation. If you try to deactivate the only admin, the API returns 400 "Cannot deactivate — this is the last admin account." This prevents full lockout.
5
Tokens are short-lived (in-memory, httpOnly cookie)
The access token is stored in-memory (not localStorage). An httpOnly cookie handles refresh. This means on browser close, the session ends. On page reload, the app re-calls /api/auth/refresh automatically to restore the session.
6
Passwords are stored plain text — handle with care
The current system stores passwords as plain text in the database (noted in project constraints). Do not expose the DB or server to the internet. Always run behind a VPN or private network until a hashing migration is implemented.
Security reminder (from .cursorrules): Passwords are stored plain text — do NOT hash without a full migration plan. When hashing is implemented, all existing passwords must be re-seeded or users forced to reset. Plan this carefully to avoid locking out all users.
